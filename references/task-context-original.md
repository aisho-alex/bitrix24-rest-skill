# Bitrix24: выгрузка задачи и связанных чатов

## Когда применять
- Есть ссылка на задачу Bitrix24 (`/tasks/task/view/<task_id>/`) — нужно её содержимое локально.
- Нужен контекст обсуждения: комментарии задачи, чат задачи, чаты из описания задачи.
- Нужно сырьё (JSON) для последующего анализа/LLM/отчёта.
- Вопросы про чаты вообще: «какие чаты есть», «что нового», «где непрочитанное»,
  «не прочитал ли я что-то важное» → режимы `--chats`, `--unread`, `--find`, `--info`.

## Ключевая идея (грабли, которые уже пройдены)
1. **Обсуждение задачи живёт в ЧАТЕ, а не в комментариях.** `tasks.task.get` отдаёт поле
   `chatId` — это чат задачи (`DIALOG_ID=chat<chatId>`). Метод `task.commentitem.getlist`
   (старые форумные комменты) на облачных порталах падает с
   `TASKID ... expected to be of type "integer", but given something else` и возвращает 0 —
   это норма, не теряйте время.
2. **В описании задачи часто лежат ссылки на другие чаты** — `IM_DIALOG=chatNNNNNN`.
   Контекст задачи реально = чат задачи + эти чаты. Скрипт сам их вытаскивает и тянет все.
3. **`im.dialog.messages.get` отдаёт сообщения от НОВЫХ к старым** и максимум 50 за вызов.
   Листать вниз по истории надо через `LAST_ID=<минимальный id из предыдущей пачки>`,
   иначе получите только последние 50 сообщений (тихая потеря истории).
4. **fast_bitrix24 для этого не годится**: `get_all()` падает на параметре `ORDER`
   (`ViolationError: get_all() doesn't support parameters 'start' or 'order'`), а `call()`
   искажает int-параметры (`order0000000000` + WRONG_ARGUMENTS). Использовать тонкую обёртку
   над REST через `requests` (в scripts/).
5. `im.chat.get` по `CHAT_ID` может вернуть `null` (нет прав у вебхука) — это не мешает,
   `im.dialog.messages.get` отдаёт и сообщения, и участников (`users`).

## Доступы
Вебхук формата `https://<portal>/rest/<userId>/<token>/`.
Порядок поиска (первый найденный побеждает):
1. `--env <файл>` или переменная окружения `BITRIX_WEBHOOK_URL`
2. `./.env` в текущей директории
3. `~/.bitrix.env`
4. `~/.config/bitrix/webhook.env`

Или напрямую `--webhook-url "https://<portal>/rest/<userId>/<token>/"`.
Вебхук видит ровно то, что видит создавший его пользователь. **Токен вебхука в чат/лог не печатать**
(в скрипте есть `redact()`; при ручном curl — маскировать).

## Запуск
```bash
# задача + её чаты
python3 scripts/fetch_bitrix_task_context.py 123456
... 123456 --out-dir ./bitrix --limit 1000          # куда писать / сколько сообщений на чат
... --dialog chat222222 --dialog chat333333          # только конкретные чаты
... --webhook-url "https://portal/rest/1/token/"     # другой портал/вебхук

# чаты и непрочитанное (см. отдельный раздел ниже)
... --chats 40            # последние 40 чатов со счётчиками непрочитанного
... --unread              # только непрочитанные + сводка im.counters.get
... --find "договор"      # поиск чатов по названию
... --info chat222222     # карточка чата: участники, кто до чего прочитал, счётчик
```
Зависимости: `requests` (`python3 -m pip install requests`).

## Что получается
```
<out-dir>/task_<id>.json             всё сырьё: карточка, users, комменты, сообщения, meta чатов
<out-dir>/task_<id>.md               карточка задачи + описание (чистый текст и raw bbCode) + список чатов
<out-dir>/task_<id>_chat<NNN>.md     читаемая переписка: [дата] Автор (id) → текст, вложения
<out-dir>/chats_recent.{md,json}     последние чаты: счётчик, тип, участники, последнее сообщение, ссылка
<out-dir>/chats_unread.{md,json}     то же, только непрочитанные + сводка im.counters.get
<out-dir>/chats_find_<запрос>.json   результат поиска чатов по названию
<out-dir>/<dialog>_info.json         карточка чата + состояние прочтения + участники
```
В markdown: bbCode вычищен, `[USER=id]` заменены на имена, системные сообщения (вход/выход из чата)
помечены, указаны период и число содержательных сообщений.

## Чаты и непрочитанное (что откуда берётся)
| Что нужно | Метод | Особенности |
|---|---|---|
| список чатов + счётчик непрочитанного + последнее сообщение | `im.recent.get` (`LIMIT`, `SKIP_OPENLINES=Y`) | основной источник; отдаёт `counter`, `unread`, `chat.type`, `chat.entity_type/entity_id`, `entity_link.url` (для чата задачи — прямая ссылка на задачу) |
| сводка непрочитанного по типам | `im.counters.get` (пустое тело) | `TYPE` (ALL/MESSENGER/CHAT/TASKS_TASK/…), списки `CHAT_UNREAD`, `TASKS_TASK_UNREAD` (там `{"<chatId>": N}`) |
| карточка чата | `im.dialog.get` (`DIALOG_ID`) | имя, тип, владелец, участников, `message_count`, `last_message_id`, `readed_list` |
| кто до чего прочитал | `readed_list` в `im.dialog.get` | НЕ включает текущего пользователя вебхука — своё прочтение смотреть по `counter` |
| участники | `im.dialog.users.list` | с должностями и статусом online |
| поиск по названию | `im.search.chat.list` (`FIND=`) | находит чаты/встречи/каналы, но НЕ чаты задач (у них имя = имя задачи, в поиск не попадают) |

Чаты бывают нескольких видов, и это важно при чтении вывода:
`tasksTask` — чат задачи (entity `TASKS_TASK <taskId>`), `sonetGroup` — чат проекта,
`calendar` — чат встречи (entity `CALENDAR <eventId>`), `private` — личка/бот
(`DIALOG_ID` = id пользователя, БЕЗ префикса `chat`).

У непрочитанного два независимых сигнала, оба в выводе: `counter` из `im.recent.get`
(сколько сообщений не прочитано именно у пользователя вебхука) и `im.counters.get`
(агрегат по порталу). Если они расходятся — верить `counter` по конкретному чату.

## MCP-сервер (для агентов: opencode, Hermes, Claude Desktop)
Отдельный проект `bitrix-mcp/` (read-only; нужны пакеты `mcp` и `requests`):
```
bitrix_mcp/client.py   REST-клиент (retry, кэш имён/проектов, маскировка токена, LAST_ID-листание)
bitrix_mcp/render.py   рендер в компактный markdown
bitrix_mcp/server.py   FastMCP: 10 инструментов, stdio (default) + --transport http --port
tools/register_opencode_mcp.py   прописать/убрать сервер в ~/.config/opencode/opencode.json
tests/smoke_mcp_client.py        смоук-тест через настоящий MCP-клиент
```
Инструменты: `bitrix_whoami`, `bitrix_find_projects`, `bitrix_project_context` (основной —
описание проекта, стадии, задачи по свежести, опционально переписка чатов задач),
`bitrix_task`, `bitrix_task_search`, `bitrix_chats`, `bitrix_chat_info`,
`bitrix_chat_messages` (со `since_id` для инкрементального добора), `bitrix_search`, `bitrix_users`.

Запуск/проверка:
```bash
cd bitrix-mcp
python3 -m bitrix_mcp.server --check      # портал + список инструментов
python3 tests/smoke_mcp_client.py         # боевые вызовы, ждём «провалов 0»
python3 tools/register_opencode_mcp.py && opencode mcp list   # «✓ bitrix24 connected»
```
Конфиг opencode: `mcp.<name> = {type: "local", command: [...], cwd, environment, enabled, timeout}` —
`timeout` ставить 45000+, дефолтные 5000 мс рвут выгрузку истории чата. Токен вебхука в конфиг
НЕ писать: сервер сам читает его из env/.env.

## Проверка результата (обязательно перед «готово»)
- В `task_<id>.md` есть заголовок, постановщик/ответственный, число чатов.
- Период каждого чата начинается с его первого сообщения, а не «обрезан» на дату создания задачи —
  если `message_count` совпал с `--limit`, история обрезана: увеличить `--limit` и перезапустить.
- В чатах-обсуждениях есть не только системные события (`CHAT_JOIN`/`CHAT_LEAVE`/«создал задачу») —
  если содержательных 0, скорее всего взят не тот диалог или у вебхука нет доступа.
- Файлы непустые и не содержат `null` вместо текста.
- Для `--unread`: сумма по чатам должна согласовываться с `im.counters.get`; если в выдаче
  0 непрочитанных, но `TYPE.ALL > 0` — увеличить `--chats` (счётчик может быть у чата,
  который не попал в первые N) либо смотреть `*_UNREAD`-списки в JSON.
- Для `--info`: если карточка чата не получена (403 на личке), статус прочтения берётся из
  `counter`; писать в ответе, откуда данные, а не «прочитано» наугад.

## Актуализация («актуализируй из <ссылка>») — повторная выгрузка и отчёт о дельте

Триггер: в директории уже лежит история по задаче (`task_<id>*.md/json`), просят «актуализировать»
или дают ту же ссылку второй раз. Смысл просьбы — не «выгрузи заново», а **что появилось нового**.
Скрипт перезаписывает файлы на месте, поэтому дельту надо готовить ДО запуска.

1. **Снять точку отсчёта до запуска** (иначе дельта потеряется):
   ```bash
   cd <dir> && for f in *.md; do echo "== $f"; head -8 "$f"; wc -l "$f"; done
   ```
   Нужны: число сообщений (`Сообщений: N`) и конец периода (`Период: ... — <TS>`) по каждому чату,
   плюс строка «изменена» из `task_<id>.md`. Ещё вариант — `cp` файлов в `/tmp` и потом `diff`.
2. Перезапустить скрипт той же командой с `--out-dir .` и `--limit 1000`.
3. Разницу считать по числу сообщений и по последнему TS прошлой выгрузки, **не по строке «Выгружено»**
   (см. TZ-грабли ниже). Новое = заголовки `### [TS]` с TS строго больше прошлого конца периода:
   ```bash
   # готовый скрипт: cutoff = старое локальное «Выгружено» из шапки
   python3 scripts/delta_since.py \
     task_<id>_chat<NNN>.md 2026-09-18T11:45:35
   # ручной вариант (всегда работает), якорь — TS первого нового сообщения с офсетом портала
   awk '/^### \[<прошлый_последний_TS>/{f=1} f' task_<id>_chat<NNN>.md
   ```
   При большом количестве сообщений резать вывод (`head -300`) и добирать хвост вторым `awk` —
   иначе тихо потеряешь последние сообщения, а они обычно самые важные.
4. Проверить карточку и состав контекста: изменилась ли строка «изменена», стадия/статус, списки
   соисполнителей/наблюдателей; не появилось ли в новых сообщениях ссылок на **другие** чаты:
   ```bash
   grep -ohE 'IM_DIALOG=[A-Za-z0-9]+' *.md | sort | uniq -c
   grep -oE 'chat[0-9]{5,7}' *.md | sort | uniq -c
   ```
   Нашлись новые диалоги — добирать точечно через `--dialog chat<NNN>` (или добавить в описание задачи).
5. Перечитать и сгруппировать новое **по темам, а не по порядку сообщений**. В отчёте отдельным
   блоком — то, что кто-то обязался сделать и к какому сроку («обещанные сроки»), и то, где нужен
   сам пользователь/его линия. Сообщения самого пользователя вебхука стоит помечать явно:
   по ним спрашивают «а что ответили на мой вопрос».
6. Формат отчёта: простой текст для терминала (без markdown-заголовков и таблиц), по-русски,
   абсолютными путями к файлам, с указанием, сколько сообщений прибавилось и в каких чатах.
   Чаты без нового — перечислить одной строкой с их «тишиной с <дата>»: это тоже ответ.

Детальный рецепт и шаблон отчёта о дельте: `references/actualization-and-delta-report.md`.

**Готовый помощник вместо ручного awk:** `scripts/task_delta.py <out-dir> [--task <id>] [--reset]`
— держит точку отсчёта в `<out-dir>/.delta_state.json` (первый запуск ставит baseline,
дальше печатает только новые сообщения по каждому чату и изменение строки «изменена» в карточке).
Цикл: `task_delta.py <dir>` → выгрузка → `task_delta.py <dir>`.
Скрипт написан 18.09.2026 и на реальных выгрузках ещё не прогонялся — при первом использовании
сверить его вывод с ручным рецептом (шаг 3 выше) на одном чате и, если формат шапки разошёлся,
поправить регулярки (`COUNT_RE`/`PERIOD_RE`/`MSG_RE`). `.delta_state.json` — служебный, не коммитить.

### Грабли актуализации
- **TZ.** Сообщения приходят с `+04:00`, локальное время машины — МСК (`+03:00`), а скрипт в шапке
  пишет время локальное. Сравнивать «Выгружено 13:32» с сообщением «14:28+04:00» без пересчёта —
  верный способ решить, что новых сообщений нет. Считайте от **последнего TS прошлой выгрузки**.
- **Скрипт перезаписывает файлы** и не пишет историю дельт. Если дельта нужна — точки отсчёта
  снимаются заранее (шаг 1), либо делается копия каталога.
- **Рост одного чата при полной тишине в других** — норма: чат задачи (`CHAT_ID`) живёт своей
  жизнью, «Основной чат обсуждения» из описания может молчать сутками. Не считать это ошибкой
  выгрузки и не тянуть повторно то, что не менялось.
- Файлы непустые и не содержат `null` вместо текста.

## Черновик сообщения в рабочий чат
Частая просьба после разбора: «сохрани описание, я кину в чат битрикса». Тут первоисточник
не переписка, а журнал проекта плюс свои наблюдения, и продукт — не отчёт, а сообщение.
- По умолчанию писать **сплошным человекочитаемым текстом**: абзацы, числа внутри
  предложений, тематический «заголовок» словом внутри строки. Таблицы, списки-простыни и
  `===`-разделители забракованы («сделай человекочитаемое описание в текстовом виде»),
  поэтому структурированный вариант — только как добавка рядом, не как основной.
- От первого лица («прогнал», «проверил»): сообщение уходит от имени пользователя.
- Обязательный последний блок — «что осталось», с адресатом по каждому пункту, и честная
  оговорка о том, чего не мерили. Числа только из источников, ничего не досочинять.
- Файл сохранять и называть абсолютным путём, текст показывать целиком (копируется из
  терминала). Класть туда, где он не уедет в чужой коммит: в `var/` (`.gitignore`)
  или в личную папку.
- Полный каркас такого сообщения (7 блоков, проверенный на живом отчёте) —
  в `references/actualization-and-delta-report.md`, раздел «Черновик сообщения в рабочий чат».

## Полезные ручные вызовы (когда нужен один факт, без полной выгрузки)
```bash
WH="$BITRIX_WEBHOOK_URL"   # или: WH=$(grep -m1 '^BITRIX_WEBHOOK_URL' ~/.bitrix.env | cut -d= -f2-)
curl -s -X POST "$WH/tasks.task.get.json" -H 'Content-Type: application/json' \
  -d '{"taskId":123456,"select":["ID","TITLE","STATUS","STAGE_ID","GROUP_ID","CHAT_ID","RESPONSIBLE_ID","CREATED_BY","DEADLINE"]}'
curl -s -X POST "$WH/im.dialog.messages.get.json" -H 'Content-Type: application/json' \
  -d '{"DIALOG_ID":"chat111111","LIMIT":50,"LAST_ID":25000000}'   # LAST_ID — листать в прошлое
curl -s -X POST "$WH/im.recent.get.json" -H 'Content-Type: application/json' -d '{"LIMIT":50,"SKIP_OPENLINES":"Y"}'
curl -s -X POST "$WH/im.counters.get.json" -H 'Content-Type: application/json' -d '{}'
curl -s -X POST "$WH/im.dialog.get.json" -H 'Content-Type: application/json' -d '{"DIALOG_ID":"chat222222"}'
curl -s -X POST "$WH/im.dialog.users.list.json" -H 'Content-Type: application/json' -d '{"DIALOG_ID":"chat222222"}'
curl -s -X POST "$WH/im.search.chat.list.json" -H 'Content-Type: application/json' -d '{"FIND":"договор"}'
curl -s -X POST "$WH/user.get.json" -H 'Content-Type: application/json' -d '{"FILTER":{"ID":[1,2]}}'
curl -s -X POST "$WH/sonet_group.get.json" -H 'Content-Type: application/json' -d '{"FILTER":{"%NAME":"Проект"}}'
```
Другие полезные методы: `tasks.task.list` (фильтр по `GROUP_ID`), `task.stages.get`
(`entityId=<groupId>` — стадии канбана), `task.stages.movetask`, `disk.attachedObject.get`
(вложения по file id из `params.FILE_ID`), `im.chat.user.list` (`CHAT_ID=` → id участников).

## Pitfalls
- `ORDER` в JSON-теле
  (`changedDate`) даёт HTTP 400. Поля `CHAT_ID` в `select` этого метода НЕТ (тоже 400) —
  chatId брать из `tasks.task.get` по каждой задаче.
- Голое число как идентификатор диалога неоднозначно: 123456 — задача, 111111 — чат.
## Pitfalls
- **Вложения через вебхук не вытянуть.** `disk.attachedObject.get` на file id отвечает
  `ERROR_NOT_FOUND`, `im.disk.file.get` — `ERROR_METHOD_NOT_FOUND` (проверено на облачном
  портале). В markdown остаются только id из «Вложения (file id): …». Не
  перебирать методы впустую: сказать пользователю, что содержимое смотрится из интерфейса,
  а в дайджесте назвать вложение по контексту сообщения.
- **Дельту считать по времени, а не по количеству.** Смещение портала (`+04:00`) против
  локальной зоны легко даёт час ошибки, и часть новых сообщений молча выпадет.
- **Часть чатов мёртвая.** Чат задачи плюс чаты из описания живут в разном темпе: один
  растёт каждый день, другой молчит неделю. Не выбрасывать молчащие из выгрузки, но и не
  ждать от них роста — так и написать.
- **Системные сообщения несут факты.** «добавил наблюдателя(ей)», «изменил стадию», «задача
  почти просрочена» — это изменения карточки, их видно в чате задачи раньше, чем в шапке.
- `ORDER` в JSON-теле (`{"ORDER":{"POST_DATE":"asc"}}`) ломает вызовы через fast_bitrix24 —
  сортировать локально.
- Вложения в сообщениях приходят только как file id (`params.FILE_ID`) — это потолок выгрузки,
  содержимое смотрится в интерфейсе портала (чем именно не получается — пункт выше).
- Задача из URL `/company/personal/user/<uid>/tasks/task/view/<id>/` — `<uid>` это НЕ всегда
  автор (в ссылке пользователя, от чьего имени открыли). Автора брать из `createdBy` карточки.
- Не печатать `BITRIX_WEBHOOK_URL` целиком (токен = полный доступ к порталу от имени вебхука).
- Выгрузка может лежать в **личной рабочей папке** пользователя — это его материал «для себя».
  Не коммитить и не добавлять в индекс без прямой просьбы.
- «Финал» в переписке не значит, что обсуждение закрыто: через 2-3 часа тема возвращается
  новым блокером. При актуализации всегда дочитывать до конца, а не опираться на прошлую сводку.
  Токен утекает в тексте ошибок `requests` (HTTPError содержит URL) — скрипт глушит их и
  маскирует токен, при ручном curl проверять вывод перед показом.
- `im.recent.get` возвращает только диалоги текущего пользователя вебхука и только последние
  (практически до 50). `id` в items — **строка с префиксом** (`"chat111111"`, `"user3"`), а не
  голое число: дописывать тип к нему нельзя, иначе `chatchat111111` →
  403/`DIALOG_ID_EMPTY` и пустой дайджест. Числовой id диалога лежит рядом в `chat_id`.
  Чата может не быть в выдаче — тогда нет и его `counter`, статус прочтения
  по нему не определить.
- `im.dialog.get` для личных диалогов (`DIALOG_ID` = id пользователя, напр. бот с id 2156)
  отдаёт HTTP 403 — это нормально, скрипт падает на резервный источник `im.recent.get`.
  Тот же 403 будет у чатов, где вебхук-пользователь не участник.
- **Форма ответа `im.dialog.messages.get` не фиксирована**: `users`
  приходит то словарём `{id: {...}}`, то **списком** `[{id, name}, ...]` — `d.update(res["users"])`
  падает с `ValueError: dictionary update sequence element #0 has length 28`. Нормализовать:
  `if isinstance(ru, list): {str(u["id"]): u for u in ru} else: ru`.
  Поле `date` — **строка** ISO (`"2026-09-21T14:48:11+04:00"`), не datetime: `.isoformat()`
  на ней падает, `str()` работает. Границу «сегодня» резать по префиксу строки, а не по дате.
- **Границу прочтения можно взять численно.** `im.dialog.get` по чату отдаёт `last_message_id`;
  `readed_list` НЕ содержит пользователя вебхука, но `counter` из `im.recent.get` — содержит.
  Если `counter == N`, то непрочитаны ровно последние N сообщений чата: это даёт точный ответ
  «что именно я не прочитал», без догадок по флагу `unread` у сообщений.
- `im.chat.get` по `CHAT_ID` у вебхука возвращает `null` — не использовать, вместо него
  `im.dialog.get` (`DIALOG_ID`) и `im.dialog.users.list`.
- Поле `unread` у каждого сообщения в `im.dialog.messages.get` малоинформативно (может быть
  `true` у старых сообщений при нулевом счётчике чата) — непрочитанное считать по `counter`
  из `im.recent.get` / `im.counters.get`, а не по этому флагу.
- `im.counters.get` вызывать с пустым телом (`{}`), иначе fast_bitrix24 падает на
  `call(): item_list can't be empty`.
